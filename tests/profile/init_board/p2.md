# Init Board 리팩토링 Phase 2 분석

## 개요

`initialize_start_map` 함수를 `initialize_board`로 리팩토링하여 코드 구조를 개선하고 DB 호출을 최적화한 결과를 분석한 문서입니다.

## 리팩토링 결과 요약

| 지표 | Before2 | After2 | 차이 |
|------|---------|--------|------|
| **실행시간** | 2,681ms | 2,703ms | +22ms (+0.8%) |
| **CPU User** | 2.540s | 2.530s | -10ms (-0.4%) |
| **메모리 Peak** | 69.6MB | 67.1MB | -2.5MB (-3.6%) |

### 핵심 개선 사항

#### 1. Sections Dictionary 전달 방식

**Before2**: 함수 내부에서 매번 DB 조회
```python
async def upgrade_interaction_sections(db: DB, sec_point: Point):
    surrounding_sections = await get_section_range(db, surrounding_range)  # DB 조회

    for neighbor_point in ...:
        await upgrade_numbering_sections(db, neighbor_point)  # 내부에서 또 DB 조회
```

**After2**: Sections dict를 인자로 전달
```python
async def initialize_board(db: DB):
    sections = {p: make_section(p) for p in init_board_range.iter()}  # 메모리에 생성

    for p in ...:
        await _upgrade_numbering_sections(db, p, sections)  # dict 전달

    await _upgrade_interaction_sections(db, center_p, sections)  # dict 전달
```

## DB 호출 분석

### 호출 횟수 비교

| DB 작업 | Before2 | After2 | 개선 |
|---------|---------|--------|------|
| **get_section_range (SELECT)** | 9회 (81개 섹션 조회) | 0회 | **-100%** |
| **create_section (INSERT)** | 9+α회 | 9회 | 중복 제거 |
| **update_section (UPDATE)** | 8회 | 9회 | +1회 |
| **update_section_flag (UPDATE)** | 9회 | 10회 | +1회 |

### Before2 호출 흐름

1. `initialize_start_map`에서 9개 Section 생성
   - `create_section`: 9회

2. `upgrade_interaction_sections` 호출
   - `get_section_range`: 1회 (9개 섹션 조회)
   - `update_section_flag`: 1회

3. 주변 8개에 대해 `upgrade_numbering_sections` 호출
   - 각각 `get_section_range`: 1회 (9개 조회) × 8 = **8회 (72개 섹션)**
   - 각각 `create_section`: for loop (중복 제외)
   - 각각 `update_section`: 1회 × 8 = **8회**
   - 각각 `update_section_flag`: 1회 × 8 = **8회**

**총 DB 조회**: 9회 (81개 섹션)

### After2 호출 흐름

1. `initialize_board`에서 메모리에 9개 Section 생성
   - `create_section`: 9회

2. 9개 섹션에 대해 `_upgrade_numbering_sections` 호출
   - sections dict 사용 (**DB 조회 없음**)
   - `update_section`: 9회
   - `update_section_flag`: 9회

3. `_upgrade_interaction_sections` 호출
   - sections dict 사용 (**DB 조회 없음**)
   - `update_section_flag`: 1회

**총 DB 조회**: 0회

## 평가

### 구조적 개선 ✅

1. **코드 분리**: 297줄 단일 파일 → 4개 파일로 책임 분리
2. **재사용성**: `_upgrade_numbering_sections`, `_upgrade_interaction_sections`를 독립적으로 사용 가능
3. **테스트 용이성**: 각 함수를 sections dict와 함께 테스트 가능
4. **확장성**: 다른 초기화 로직에서도 동일한 패턴 재사용 가능

### DB 최적화 효과 ⚠️

1. **호출 횟수**: 9회 SELECT (81개 섹션) → 0회 (**100% 감소**)
2. **실행 시간**: 0.254s → 0.258s (+0.004s)
3. **원인**: DB 작업이 전체의 10%밖에 차지하지 않음
4. **환경적 요인**:
   - SQLite + aiosqlite 로컬 파일 DB
   - 네트워크 지연이 없어 조회 비용이 낮음
   - Section 객체가 작아 직렬화/역직렬화 비용 낮음

### 성능 영향 분석

**개선된 부분**:
- 메모리 Peak: 69.6MB → 67.1MB (-3.6%)
- DB 중복 조회 제거

**악화된 부분**:
- numbering 시간: 1.700s → 1.937s (+0.237s)
- rand_tiles 시간: 0.337s → 0.490s (+0.153s)

**총합**: 미세한 성능 저하 (+22ms, +0.8%)

## 결론

### 리팩토링 가치

이 리팩토링은 **성능 개선보다는 코드 품질 개선**을 목표로 한 작업입니다.

**긍정적 성과**:
- DB 조회 100% 제거 (구조적 개선)
- 코드 가독성 및 유지보수성 향상
- 함수 책임 분리 및 재사용성 증가
- 테스트 용이성 개선

**성능 결과**:
- DB 최적화 효과는 미미함 (병목이 아니었음)
- 전체 실행 시간은 거의 동일
- 메모리는 소폭 개선

### DB 최적화의 한계

DB 작업이 전체의 10%밖에 차지하지 않아, 100% 제거해도 성능 개선이 크지 않았습니다.

**병목은 알고리즘**:
- `count_mine` (1.3초, 48%)
- `PointRange.iter` (0.4초, 15%)
- `Random.randint` (0.3초, 11%)

향후 성능 개선을 위해서는 이 부분의 최적화가 필요합니다.

### 미래 가치

이 리팩토링은 다음 상황에서 빛을 발할 수 있습니다:
- 원격 DB (PostgreSQL, MySQL 등) 사용 시 네트워크 지연 감소
- Section 크기 증가 시 직렬화 비용 감소
- 초기화 범위 확대 시 (3×3 → 5×5 등) 조회 횟수 증가 방지
