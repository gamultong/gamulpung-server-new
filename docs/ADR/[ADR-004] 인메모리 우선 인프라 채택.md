# 인메모리 우선 인프라 채택

## 상황
이벤트 브로커와 obj 저장소의 인프라를 선택해야 했다. Kafka·RabbitMQ 같은 외부 브로커나 외부 저장소 도입이 후보였다.

## 결정
인메모리를 기본으로 한다. 브로커는 자체 구현 인메모리 pub/sub을 쓰고, obj 저장은 인메모리 구조와 SQLite를 쓰되 Storage/Space 인터페이스 뒤에 두어 외부 인프라로의 교체에 대비한다.

## 근거(요약)
- 현재 규모에 외부 브로커 도입은 과한 설계다.
- 인메모리 큐를 기본 베이스로 해야 이후 Kafka·RabbitMQ로의 마이그레이션 확장성이 좋다.
- 저장소는 인터페이스로 추상화되어 있어 필요해질 때 교체하면 된다. Board 저장은 실제 확장(SQLite 영속) 사례가 있다.
- Event payload를 식별자 중심으로 최소화하고 Receiver가 처리 시점에 최신 상태를 fetch하므로, 브로커의 전달 시점·순서 의미론에 대한 의존이 낮다. 인터페이스만이 아니라 이 약한 결합이 외부 브로커 마이그레이션을 실제로 가능하게 한다.
- 예외적으로 변경 이전 snapshot은 fetch로 복원할 수 없으므로 payload에 실어 보낸다. fetch가 줄 수 없는 것(과거)만 이벤트가 운반한다. ([원문 답변](/docs/Other/Design%20QnA%202026-06.md))
